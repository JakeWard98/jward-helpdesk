# Email

## Proton Mail

Proton splits sending and receiving, and they are configured differently.

| Direction | How | Needs |
| --- | --- | --- |
| **Sending** | Proton SMTP submission, `smtp.protonmail.ch:587` | A Proton **Business** plan and a custom domain. Generate an SMTP token in the Proton admin panel. |
| **Receiving** | Proton Mail **Bridge**, local IMAP | Mail Plus, Unlimited or Business. Bridge runs as a process or container and exposes IMAP on `:1143`. |

There is **no public Proton IMAP endpoint** — if you skip Bridge, the helpdesk
runs send-only: replies you write in the GUI are emailed out, but nobody can
email in. That is a supported configuration, just set
`INBOUND_EMAIL_ENABLED=false`.

### Sending (SMTP submission)

In Proton: **Settings → All settings → IMAP/SMTP → SMTP submission → Generate
token**. The token is tied to one address, and Proton rejects mail whose `From`
is anything else.

```
SMTP_HOST=smtp.protonmail.ch
SMTP_PORT=587
SMTP_SECURITY=starttls
SMTP_USERNAME=helpdesk@yourdomain.com
SMTP_PASSWORD=<the SMTP token>
SMTP_FROM_EMAIL=helpdesk@yourdomain.com   # must match the token's address
SMTP_FROM_NAME=Helpdesk
SMTP_REPLY_TO_EMAIL=helpdesk@yourdomain.com
```

Certificates are verified normally here — Proton's are publicly trusted, so
leave `SMTP_CA_CERT` and `SMTP_TLS_INSECURE` alone.

### Receiving (Proton Mail Bridge)

Bridge has to run somewhere the worker container can reach. The usual homelab
answer is a container in the same stack, e.g. `shenxn/protonmail-bridge`, which
you log into once interactively and which then listens on `1025` (SMTP) and
`1143` (IMAP).

```
INBOUND_EMAIL_ENABLED=true
IMAP_HOST=protonmail-bridge
IMAP_PORT=1143
IMAP_SECURITY=starttls
IMAP_USERNAME=helpdesk@yourdomain.com
IMAP_PASSWORD=<the Bridge password, shown in the Bridge UI>
IMAP_FOLDER=INBOX
IMAP_PROCESSED_FOLDER=Processed
```

Bridge presents a **self-signed certificate**, so one of these is also needed:

- `IMAP_CA_CERT=/certs/bridge.pem` — export the certificate from Bridge and
  mount it into the worker container. Verification stays on. **Prefer this.**
- `IMAP_TLS_INSECURE=true` — skips verification. The app only accepts this when
  the host is loopback, a private address, or a bare container name, and
  refuses at boot otherwise. Acceptable for a bridge on the same docker
  network; not acceptable for anything reachable off the host.

If Bridge runs on the host rather than in the stack, use
`IMAP_HOST=host.docker.internal` and add to the `worker` service:

```yaml
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

The Bridge password is not your Proton password — it is generated by Bridge and
shown in its interface.

## Any other provider

Nothing above is Proton-specific except the hostnames. A normal mailbox with
IMAP and SMTP works with no bridge:

```
SMTP_HOST=smtp.example.com   SMTP_PORT=587   SMTP_SECURITY=starttls
IMAP_HOST=imap.example.com   IMAP_PORT=993   IMAP_SECURITY=ssl
```

Use an app password wherever the provider offers one.

## The round trip

```
someone emails helpdesk@yourdomain.com
        │
        ▼
worker polls IMAP every IMAP_POLL_SECONDS
        │
        ▼
ticket TKT-1042 created on the fallback template ("Something else")
        │
        ▼
acknowledgement sent:
   Subject: [TKT-1042-9f3c1ab27d0e] Netflix keeps buffering
   ...
   [ref:1042-9f3c1ab27d0e]          <- in the footer
        │
        ▼
you reply in the GUI  ──▶  queued in outbound_emails  ──▶  worker sends it
        │
        ▼
they hit reply in their mail client
        │
        ▼
worker matches the signed reference, appends to TKT-1042
        │
        ▼
you see it in the timeline; they see it in their portal view too
```

## How a reply is matched

The ticket reference is **never** put in the email address. Plus-addressing
(`helpdesk+t.1042@…`) is not reliable across providers and is the first thing a
forwarding rule rewrites. Instead the reference travels in two places, and is
signed both times:

`HMAC(APP_SECRET, "<ticket number>:<ticket.reply_token>")`, truncated to 12 hex
characters. `reply_token` is 16 random bytes stored on the ticket, so one
ticket's reference reveals nothing about another's.

Matching order, first hit wins:

1. **Signed subject tag** — `[TKT-1042-9f3c1ab27d0e]`. Survives a normal
   `Re:` reply.
2. **Signed body reference** — `[ref:1042-9f3c1ab27d0e]`, searched for
   anywhere in the raw body *including the quoted history*. This is what
   catches a reply where the sender rewrote the subject line.
3. **Threading headers** — `In-Reply-To` / `References` matched against
   `Message-ID`s the helpdesk sent or previously ingested.
4. **Bare subject tag** — `[TKT-1042]` with no signature, accepted **only**
   from the requester, from staff, or from someone who has already written on
   that ticket. Ticket numbers are sequential, so without that restriction
   anyone could guess one and post into a stranger's ticket.

No match means a new ticket on the fallback template, which you re-template
from the ticket page.

Every message is recorded in `processed_inbound_emails` by `Message-ID`, so
re-reading a folder never duplicates a ticket. Mail arriving without a
`Message-ID` gets a synthetic one derived from a hash of the raw bytes.

### If you rotate `APP_SECRET`

Every previously issued reference stops verifying. Threading headers still
match older threads, and the bare subject tag still works for participants, so
the damage is limited — but expect a few replies to land as new tickets. Merge
them by hand.

## Loop protection

- Mail from the helpdesk's own address is ignored outright.
- An auto-reply (`Auto-Submitted`, `X-Autoreply`, `Precedence: bulk`, or an
  "Out of office" subject) that matches no ticket is dropped instead of
  creating one. If it matches a ticket it is logged on the timeline, and no
  acknowledgement goes back.
- Outbound mail carries `Auto-Submitted: auto-replied` and
  `X-Auto-Response-Suppress`, telling well-behaved responders not to answer.

## Attachments

Everything attached to an inbound message is stored and appears on the ticket:

- **Inline images** (`Content-ID`, referenced as `cid:` in the HTML body) are
  rewritten to `/api/attachments/<id>/inline` and render in the message body.
- **Regular attachments** are listed under the message and download on click.
- **Remote images** (`<img src="https://…">`) are removed and the message is
  marked "Images hosted elsewhere were removed from this email." That kills
  tracking pixels and stops your IP leaking to the sender.

Anything over `MAX_ATTACHMENT_MB` (default 25) is skipped with a warning in the
worker log; the message itself is still ingested. A whole email over
`MAX_EMAIL_MB` (default 40) is dropped.

Files you attach to a reply in the GUI are sent with the outgoing email.

## Outbound queue

The API never opens an SMTP connection. It writes to `outbound_emails` in the
same transaction as the ticket message, and the worker sends it. So a slow mail
server never blocks the GUI, a restart mid-send loses nothing, and the API
container needs no network egress at all.

Failed sends retry with quadratic backoff (1, 4, 9, 16, 25 minutes) up to six
attempts, then stop and show under **Admin → Mail** as failed.

## Troubleshooting

### Nothing is being ingested

```bash
docker logs -f helpdesk-worker
```

`IMAP poll failed` usually means Bridge is not running, not logged in, or not
reachable from the worker container. Check with:

```bash
docker exec helpdesk-worker python -c \
  "import socket; print(socket.create_connection(('protonmail-bridge', 1143), 5))"
```

Also note the worker only reads **unread** mail. If you have been testing by
opening messages in a mail client first, they are skipped.

### `certificate verify failed` against Bridge

Expected — Bridge is self-signed. Set `IMAP_CA_CERT` to its exported
certificate, or `IMAP_TLS_INSECURE=true` if the bridge is on the local docker
network.

### The app refuses to start: "IMAP_TLS_INSECURE is set but IMAP_HOST is not local"

Working as intended. Skipping verification is only permitted for a loopback,
private or container-name host. Supply `IMAP_CA_CERT` instead.

### Proton rejects outgoing mail

Almost always `SMTP_FROM_EMAIL` not matching the address the SMTP token was
issued for. SMTP submission also needs a Business plan and a custom domain — a
`@proton.me` address cannot use it.

### Replies create new tickets

Look at an email the helpdesk actually sent:

- Subject should start `[TKT-<number>-<12 hex characters>]`.
- The footer should carry `[ref:<number>-<same 12 characters>]`.

If both are present and replies still miss, the sender's client is stripping
the subject tag *and* not quoting the body — rare. The worker log records which
signal matched (`signed-subject`, `signed-body-ref`, `threading-headers`,
`unsigned-subject`, `none`), which tells you what is surviving the round trip.

If `APP_SECRET` was changed, see [above](#if-you-rotate-app_secret).

### Emails queue but never send

`docker logs helpdesk-worker` shows the SMTP error. Check the `worker`
container is attached to the `egress` network — it is the only service allowed
out to the internet.
